# 0008: MediaTool — CLI-процесс ffmpeg с гибридной загрузкой

## Status

Принято. Применяется в фиче `media-ffmpeg` (см. `docs/features/media-ffmpeg/spec.md`).

## Context

В ядре Tubeloader контракт `MediaTool` (`core/.../port/MediaTool.kt`) объявлен как порт
для операций над медиафайлами: `mux(videoTrack, audioTrack, output, onProgress)` и
`remux(input, output, onProgress)`. Адаптер Rutube уже зовёт `MediaTool.remux` в
`finalize`; реализации в репозитории нет.

Спека ядра (`docs/features/core/spec.md`, раздел «MediaTool») оставляет выбор формы
реализации открытым: «реализация транслирует вызов либо во встроенную библиотеку,
либо в аргументы внешнего CLI-процесса». `tech-stack.md` отмечает FFmpeg как
внешний инструмент «за портом `MediaTool`», не уточняя форму. Спека адаптера Rutube
(`docs/features/rutube-adapter/spec.md`, Out of Scope) выносит реализацию `MediaTool`
за пределы адаптера: «реальный `MediaTool` поставляется инфрой», форму инфраструктуры
не фиксирует.

История прототипа (`docs/archive/prototype/`) — JAVE: Java-обёртка над ffmpeg,
поставлялась как зависимость приложения. Прототип снесён, JAVE вместе с ним. Это
оставляет выбор «как реализовать `MediaTool`» открытым, и его надо закрыть, прежде чем
писать код.

Параллельно — политика распространения ffmpeg. JAVE тащила свой ffmpeg в JAR; для новой
реализации возможны три позиции: (а) ffmpeg лежит в репозитории приложения как
бинарный ресурс; (б) ffmpeg скачивается при первом запуске с публичного источника;
(в) гибрид — если уже распакован, берём; иначе скачиваем.

## Decision

Реализация `MediaTool` — `FfmpegMediaTool` в пакете `core.media` (внутри `:core`),
обёртка над внешним CLI-процессом `ffmpeg`. Процесс запускается на каждый вызов
`mux`/`remux`; долгоживущего процесса нет. Отмена корутины операции гасит дерево
процессов через `ProcessHandle.destroyTree()` — это и есть процессная изоляция,
обещанная контрактом.

Распространение ffmpeg — **гибрид**: при первом обращении к `MediaTool` реализация
проверяет, есть ли `~/.tubeloader/ffmpeg/ffmpeg(.exe)` (источник пути —
`MediaToolConfig.homeDir`, общий с `common:config/DefaultSources.kt::defaultSources`).
Если есть и исполним — использует его. Если нет — скачивает официальный статический
бинарник с публичного источника (`gyan.dev` для Windows, `johnvansickle.com` для
Linux, `evermeet.cx` для macOS), проверяет SHA-256 из соседнего файла источника,
распаковывает в `~/.tubeloader/ffmpeg/`. Последующие запуски переиспользуют уже
распакованный файл. URL, SHA-256, целевая версия — `private const` реализации, не
пользовательский конфиг.

Скачивание идёт через стандартный `java.net.http.HttpClient`, не через `HttpTool`.
У скачивания один сценарий (один GET при первом запуске, без прогресса, без
ретраев, сбой виден как `IOException`); ради него тянуть Ktor + CIO + encoding в
`:core/media` — лишний шум. Контракт `HttpTool` остаётся единственной публичной
сетевой поверхностью ядра. Если у реализации появятся дополнительные сетевые
сценарии, переход на `HttpTool` рассматривается отдельно.

`MediaToolConfig` — новый объект в `core.config`: `homeDir: Path` (обязательное) и
`binaryPath: Path? = null` (опциональный escape hatch для CI и тестов). Никаких
других полей: версия, URL, хеши — внутреннее.

## Consequences

**Положительные.**
- CLI-процесс естественно даёт процессную изоляцию: падение ffmpeg не роняет JVM,
  версия ffmpeg не привязана к зависимости в `gradle/libs.versions.toml`, обновление
  ffmpeg — смена `private const` + ADR, без пересборки приложения.
- Гибридная загрузка не требует дистрибутива ffmpeg в репозитории (вес,
  лицензионные уведомления) и не требует наличия ffmpeg в PATH на машине
  пользователя (отдельная инструкция по установке). Бинарник лежит в
  пользовательском каталоге, общем с `config.toml` — единое место для
  пользовательских данных приложения.
- `ProcessHandle.destroyTree()` — это именно то, что обещает контракт
  («гасит дерево процессов запущенного инструмента целиком, осиротевших
  дочерних процессов не остаётся»), без сюрпризов в реализации.
- `MediaToolConfig` с `homeDir` + `binaryPath` снимает нагрузку с тестов:
  подмена пути в конфиге — не подмена системного свойства.

**Отрицательные.**
- Холодный старт первой загрузки включает скачивание и распаковку ffmpeg — на
  хорошей сети десятки секунд, на плохой может упасть. Это видно как
  `Result.failure(IOException)` от первой операции `mux`/`remux`. Согласовано с
  контрактом («сбой инструмента виден как `Result.failure` самой операции»), но
  является наблюдаемым поведением для пользователя.
- Зависимость от публичного источника: смена URL на стороне источника ломает
  скачивание. URL — `private const`, изменение требует правки кода. Это сознательный
  обмен: «доверяй URL, но дай пользователю escape hatch через `binaryPath`».
- Юридический вопрос: ffmpeg — LGPL/GPL, формально уведомление о лицензии
  рекомендуется, если приложение распространяет бинарник. В текущей форме
  (скачивание с официального источника) приложение бинарник не распространяет, и
  уведомление не обязательно. Это правовой вопрос, не технический; решение
  откладывается до изменения формы распространения. ADR фиксирует отложенность.
- Версия Java: `ProcessHandle.destroyTree()` появился в Java 9; `java.net.http.HttpClient`
  — в Java 11. Это нижняя планка для запуска приложения. Текущий toolchain (по
  `core/build.gradle.kts`) — Java 21, запас большой.
- Каждая операция `mux`/`remux` — холодный старт процесса ffmpeg. Для длинных
  remux это лишние сотни миллисекунд по сравнению с нативной либой. В M1 это
  приемлемо; оптимизация (пул процессов, прогрев) — отдельный тикет.

**Альтернативы, которые отвергли.**

1. **Нативная либа (JCodec / Bytedeco `ffmpeg-platform` / JAVE2).** Снимает холодный
   старт, убирает зависимость от публичного URL и Java-версии. Минус: нативный
   артефакт под каждую ОС/arch в репозитории, кросс-сборка под Windows/Linux/macOS —
   отдельная головная боль, лицензия/уведомления переезжают в приложение.
   Прототип шёл этим путём через JAVE; отказ от JAVE был про форму распространения,
   не про саму идею нативной либы. CLI-процесс даёт те же свойства (изоляция,
   версионирование), но без нативной сборки в репо. Замена на нативную либу —
   отдельный тикет, если производительность станет узким местом.

2. **ffmpeg в ресурсах `:core` (или отдельного модуля).** Детерминированная сборка,
   нулевая зависимость от публичного источника, версия известна в момент сборки.
   Минус: бинарник ffmpeg в репозитории — это перенос дистрибутива в приложение;
   размер артефакта (десятки мегабайт × 3 ОС) заметен; лицензионные уведомления
   переходят в приложение. Гибрид даёт «бинарник рядом с пользовательскими
   данными» без хранения в репо.

3. **Скачивание ffmpeg на каждый старт без кеша.** Минимальный код, но
   нерабочая производительность: ffmpeg — десятки мегабайт, и качать его на
   каждый запуск приложения нельзя.

4. **ffmpeg из системного PATH, без скачивания.** Минимально, но требует от
   пользователя ручной установки и обработки «ffmpeg не найден» как
   пользовательской ошибки. Это уход от цели фичи (см. user story 2: «первая
   загрузка после установки отработала без ручной установки»).

5. **Скачивание через `HttpTool`.** Семантически чище (тот же сетевой шов, что и
   у адаптеров), но `HttpTool` оптимизирован под retry-семантику, прогресс
   через колбек, диапазон статусов — для одного GET при холодном старте это
   избыточно. Если у `MediaTool` появятся дополнительные сетевые сценарии
   (обновления, зеркала), переход на `HttpTool` рассматривается отдельно.

**Что меняется в коде при пересмотре этого решения.**
- Замена CLI-процесса на нативную либу: новая реализация `MediaTool` в том же
  пакете `core.media`, адаптеры и ядро не правятся, контракт `MediaTool` не
  меняется.
- Смена источника скачивания: правка `private const URL` внутри `FfmpegMediaTool`.
- Удаление скачивания (только `binaryPath` из конфига): правка реализации,
  `MediaToolConfig.binaryPath` становится обязательным.
