# Очередь загрузок: конфайнмент одного воркера

Ядро ставит загрузки в единую FIFO-очередь с глобальным лимитом параллельных задач (конфиг
приложения, дефолт 3, минимум 1). Очередь владеет только исполнением: принимает лямблу запуска
задачи, стартует её корутиной на конфайн-диспетчере, выдаёт слот по текущему лимиту и
освобождает по завершении. Про статусы очередь не знает ничего. Жизненный цикл задачи
(состояния, `TaskId`, `startedAt`/`finishedAt`) принадлежит фасаду: `TaskId` резервируется CAS-ом
по карте состояний (реестр задач, `TaskRegistry`), отменой владеет `DownloadHandle`. Конкурентность очереди
решена конфайнментом: все мутации её структур исполняются на единственном воркере
однопоточность которого очередь получает снаружи — инжектированным диспетчером (продакшн-значение
— `Dispatchers.Default.limitedParallelism(1)`); обычные структуры безопасны без блокировок.
Конфайнмент — свойство очереди, а не следствие дефолта в ядре: скоуп ей передаёт сборка
приложения, и свой она заводит дочерним от переданного — вместе с правом погасить только его.
Сама работа задачи в этом воркере не исполняется: очередь получает второй контекст исполнения
(продакшн-значение — `Dispatchers.IO`) и запускает лямблу в нём через `withContext`, иначе
блокирующее чтение тела ответа заняло бы единственный воркер и выродило параллельные загрузки
в последовательные; слот удерживается от старта работы до её завершения, а освобождение слота и
`pump()` возвращаются на конфайн-воркер. Лимит очередь читает из переданной конфигурации — поток
`StateFlow<AppConfig>` держит сборка приложения, команд смены конфигурации у ядра нет, — а
остановка — её собственная операция: отмена своего скоупа и ожидание фактического завершения с
бюджетом времени, идемпотентно (тикет 13).

## Considered Options

- **Конфайнмент одного воркера** (принято): мутации сериализуются без блокировок и CAS; FIFO
  задаётся сам; смена лимита в рантайме — чтение нового значения воркером. Не наследует гонки
  плейсхолдера `jobs` в `DownloadDispatcher` (put/cancel из потока вызывающего, remove на воркере).
- **Channel-актор с типизированными командами** (отклонён): та же сериализация, но синхронный
  контракт `enqueue` — выделение `TaskId` и публикация `Queued` обязаны произойти до возврата из
  команды; почтовый ящик уводит это в асинхронщину и контракт ломает (тот же аргумент, которым
  отклонён перенос `transition(Queued)` внутрь `launch`, тикет 13).
- **Semaphore поверх CAS-структур** (отклонён): `Semaphore` kotlinx не позволяет менять
  `maxPermits` после создания — ломает смену лимита в рантайме.
- **Общая мутабельная карта + блокировки** (отклонён): карта задач — гонка-опасна;
  расширять эту модель до очереди — умножать точки синхронизации.

## Consequences

- Отдельная очередь для MediaTool не вводится: лимит задач ограничивает и параллельные запуски
  инструмента; contention, если появится, закрывается семафором внутри реализации порта.
- Однопоточность инжектированного диспетчера — часть контракта очереди, а не следствие её кода:
  очередь не проверяет его и не оборачивает `limitedParallelism`: подмена на многопоточный
  диспетчер ломает FIFO-структуры без единой ошибки компиляции.
- Замена модели — переработка одного класса (реестра задач); публичный шов (фасад: команды +
  `DownloadHandle`) не меняется.
