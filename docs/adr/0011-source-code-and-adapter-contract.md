# 0011: Код источника и контракт адаптера

## Status

Принято. Требования зафиксированы в `docs/features/core/spec.md`,
`docs/features/usecases/spec.md`, `docs/features/smoke/spec.md`; реализация — тикеты в
`## Tickets` этих спек. Форма `MediaResult.Failed(error, cause)` уточнена тикетом #135.

## Context

Идентичность источника сейчас — позиция в списке: `Source(SourceId(index), displayName)`, где
`SourceId` — порядковый номер регистрации (`core/.../facade/CoreFacade.kt`, `mapIndexed`).
Адаптеры регистрируются списком `List<SourceAdapter>`. Имя `SourceId` вводит в заблуждение:
это индекс, а не идентификатор, и он меняется от перестановки адаптеров.

Контракт адаптера — `find(input)` (разбор URL) и `loadMeta(id)` (данные по идентификатору).
Фасад поверх них держит `findByUrl`, `findById(SourceId, mediaId)` и `loadMeta(ref)`. Вход по
идентификатору сломан: `findById` выбирает адаптера по индексу и зовёт у него `find(id)` — то есть
просит адаптер разобрать идентификатор как URL. Настоящие адаптеры URL и ждут: `RutubeSourceAdapter.find`
на хосте Rutube без пути возвращает `Unsupported`, `YoutubeSourceAdapter.find` на не-youtube-хосте — тоже.
Тесты это не ловят: `FakeSourceAdapter` отвечает `Found` на любой вход.

Прикладной слой разводит разрешение на два вызова: `ResolveUrl` даёт `MediaRef`, `LoadMedia` даёт
метаданные. Смоук умеет адресовать только Rutube: `-id` жёстко строит `https://rutube.ru/video/<id>/`.

Источник нужен как публичное значение: фронтенд должен уметь сказать « Rutube, вот такой-то id », а
ссылка на источник не должна ломаться от переименования подписи или перестановки источников.

## Decision

**Идентичность источника — код.** `Source(code, displayName)`: код — постоянный идентификатор
источника (`rutube`, `youtube`), задаётся при регистрации, всегда в нижнем регистре, непустой и
уникальный; подпись — для человека. `SourceId` удаляется: идентификатора-позиции у источника нет.

**Регистрация — карта.** Адаптеры регистрируются как `Map<String, SourceAdapter>`, ключ — код.
Карта отдаёт ядру и набор источников, и карту «код → адаптер» для разрешения по коду. Дубль кода —
ошибка сборки, а не молчаливая замена адаптера.

**Контракт адаптера — две операции.** `resolveId(input)` разбирает URL источника в идентификатор
медиаэлемента, без сети: исход `ResolveIdResult` (`Found` / `Unsupported` / `NotFound`).
`findById(id)` отдаёт данные о медиаэлементе по идентификатору, с обращением к источнику: исход
`LoadMetaResult` (`Found` / `NotFound` / `Failed`). `find` и `loadMeta` уходят.

**Роутинг URL остаётся в ядре.** Ядро перебирает зарегистрированные источники и берёт того, чей
`resolveId` вернул идентификатор; url-шаблоны источника живут в самом источнике. Неоднозначный матч —
ошибка.

**Фасад отдаёт данные о медиаэлементе.** `findByUrl(input)` и `findById(code, mediaId)` возвращают
`MediaResult`: `Found(ref, meta)` / `NotFound` / `Unsupported` / `Failed(error, cause)`. Метаданные приезжают
вместе со ссылкой; отдельной операции «загрузить метаданные» у ядра нет. `findById` источник не
ищет — код уже назван, ядро собирает ссылку и идёт за данными через `findById` адаптера.

**Прикладной слой — один use-case.** `ResolveMedia.byUrl(input)` / `ResolveMedia.byId(code,
mediaId)` заменяют пару `ResolveUrl` + `LoadMedia`.

**Смоук — адресация кодом.** Цель `-id <code>:<mediaId> -name <name>`: код источника и
идентификатор медиаэлемента. Код приводится к нижнему регистру; неизвестный код — ошибка команды
со списком известных кодов, до старта загрузок.

## Considered Options

- **Оставить идентификатор-позицию.** Отвергнуто: позиция — свойство регистрации, а не источника;
  ссылка «код:идентификатор» ломалась бы от перестановки адаптеров, и в URL она нечитаема.
- **Взять `displayName` как код.** Отвергнуто: подпись для человека, её правка ломает ссылки;
  «YouTube» и «youtube» — два разных ключа.
- **Отдельный тип `SourceCode` вместо `String`.** Отвергнуто: нормализация в одном месте не
  окупает тип; код приводится к нижнему регистру при регистрации и при разборе команды, ядро
  сравнивает точно.
- **Адаптерный `findById` без сети (только формат id).** Отвергнуто: проверка существования уже
  есть в загрузке данных, второй сетевой вызов — двойная работа; кроме того, «ищет» тут означало бы
  «не ищет», имя вводит в заблуждение.
- **Оставить `loadMeta` и добавить `findById`.** Отвергнуто: две операции с одинаковым смыслом и
  разными именами — источник ошибок.
- **Оставить `ResolveUrl` и `LoadMedia` раздельно.** Отвергнуто: разрешение — одна операция ядра,
  разводить её на два вызова на прикладном слое незачем.

## Consequences

**Положительные.**
- Вход по идентификатору работает: источник назван, адаптер получает идентификатор, а не URL.
- Ссылка на источник стабильна: код не зависит ни от подписи, ни от порядка регистрации.
- Один исход на операцию разрешения: `MediaResult` вместо двух типов, которые вызывающий
  комбинировал вручную.
- URL-шаблоны остаются в источниках: ядро не знает про rutube.ru и youtube.com.

**Отрицательные.**
- Ломается публичный контракт расширения: `find`/`loadMeta` → `resolveId`/`findById`, удаляется
  `SourceId`. Правки касаются обоих адаптеров, contract-набора, фасада, прикладного слоя и тестов.
- `findById` в адаптере и в фасаде — одно имя при разных арностях: у адаптера `findById(id)`
  отдаёт метаданные, у фасада `findById(code, mediaId)` — ссылку с метаданными.
- Карта регистрации не даёт порядка: список источников для показа пользователю придётся упорядочивать
  отдельно, когда появится фронтенд.
