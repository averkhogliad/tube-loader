# CI-скрипты: зоны ответственности

Источник истины по разграничению CI-скриптов на слои. Разделение не зависит от CI-провайдера.

- `scripts/weeek/` — интеграция с Weeek API: составляет сообщения и отправляет их. Свой конфиг —
  рядом со скриптом; провайдерские ключи из окружения (`branchPath`, `prPath`) читает, но чужих
  конфигов не открывает.
- `scripts/ci/` — сбор данных, не зависящий от провайдера: диапазон коммитов, авторы, номера
  задач. Конфиг свой, рядом со скриптами.
- `.github/scripts/` — оркестрация флоу провайдера и всё платформо-специфичное. Конфиги лежат рядом со скриптами.
- Провайдерский скрипт тонкий: собирает runtime-данные события, передаёт их значениями и
  делегирует вызовы в `scripts/ci` и `scripts/weeek`. Логики сбора данных и доменной логики в нём
  нет.
- Логика не дублируется между провайдерами. Допустимое дублирование — вызов общего скрипта с
  передачей значений.
- Провайдерский слой не читает конфиги других слоёв.
- Домен не знает, кто его вызвал: хост ссылок и адреса приходят снаружи. Провайдерский конфиг
  обязан задать ключи, которые домен читает из окружения: `webBase` и `tokenEnv` — всегда,
  `branchPath` и `prPath` — те флоу, которые строят ссылку на ветку или PR; без них домен
  завершается ошибкой.
- Платформенные данные, обогащающие сообщение (ссылки, профиль автора), провайдер передаёт домену
  значениями: шаблон ссылки на коммит и команда разрешения профиля автора
  (`--commit-path`/`--author-url-command`) — параметры вызова `scripts/ci`, а не логика внутри него.
- Добавление нового провайдера: конфиг рядом со своим адаптером, адаптер-обёртка, воркфлоу. Правок
  в `scripts/ci/` и `scripts/weeek/` быть не должно.

## Как проверяется

`grep`-пробами: в провайдерском слое не встречается `git log` и нулевой sha; общие слои не знают
имён провайдеров и хостов; провайдерский слой не ссылается на чужие конфиги.

## После мутации перечитать состояние отдельным вызовом

Скрипт, который меняет внешнее состояние (ветка, метки, карточка), не докладывает результат
своим же выводом: многошаговый скрипт печатает состояние, снятое до последнего шага. Скрипт с
`git checkout` и `git branch -D` в одном вызове отчитывается о ветке, с которой только что ушёл.

Правило: после любой мутации состояние читается **отдельным** вызовом, и только он считается
доказательством.

- Ветка: `git rev-parse HEAD`, `git branch --show-current`, `git status --porcelain` — после
  переключения/создания/удаления, а не строкой из того же скрипта.
- Метки в `scripts/tracker/tracker.mjs`: `issue create --label` и `issue edit --add-label` **задают
  набор меток целиком** — `PATCH` уходит с `labels: [...]` (`tracker.mjs:254`), и всё, чего в
  списке нет, снимается; повторный `--add-label` в одной команде теряется, парсер оставляет
  последнее значение флага. Несколько меток — одним флагом через запятую, затем `issue view`.
- Редактор кода: успешный ответ инструмента об изменении файла проверяется чтением файла или
  `git diff`, иначе правка может остаться только в ответе.

**Why:** мутация без перечитывания даёт ложный отчёт того же вида, что и успех: команда
отвечает `200`, состояние в выводе выглядит правильным, а изменение не применилось или уже
отменено следующим шагом.
**How to apply:** любую проверку «что получилось» писать отдельным вызовом после мутирующего;
при сомнении — читать состояние дважды (до и после).
