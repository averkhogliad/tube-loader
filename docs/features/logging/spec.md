# Логирование: фасад и backend

Спека введения логирования. Стековое решение — `docs/adr/0013-logging-slf4j-logback.md`.
Смерть шпиона `LoggingHttpTool` — фича failure-reason (#135); смерть `System.err`-механики
smoke — здесь. Тикеты независимы.

## Problem Statement

Единственный логирующий код — `FfmpegMediaTool` (`:infra`): три диагностических сообщения прямо
в `System.err` (недоступность инструмента, командная строка, провал операции). Прямые записи в
`System.out`/`System.err` из модулей обходят любой шов: композиция smoke перехватывает stderr
целиком (`System.setErr` + `LineSinkStream`), чтобы вернуть строки на дашборд. Ручной префикс
вместо имени логгера, уровней нет, приёмник не сменить без правки модуля. Ядро диагностику не
логирует — она едет значениями; логирование — забота слоёв реализации и композиции.

## Solution

Стек по ADR-0013: фасад `slf4j-api` в логирующих модулях, backend выбирает композиция; первый —
`logback-classic` в `:tools:smoke` (программный console-аппендер, место под кастомный аппендер
дашборда). Kotlin-делегат `val logger by slf4j()` в `:infra` — имя логгера по классу, перегрузки
по имени/KClass. `FfmpegMediaTool` мигрирует: недоступность — warn, команда — info, провал —
warn; ручной префикс умирает. `System.setErr`-перехват и `LineSinkStream` удаляются: нота с
командой ffmpeg остаётся в stderr-логе backend'а — осознанная потеря заметки на дашборде
(недоступность отмечает `SmokeTools`, провалы едут через `DownloadState.cause`). Версии — только
`gradle/libs.versions.toml`.

## User Stories

1. Как разработчик, я хочу логировать через фасад, а не в `System.err`, чтобы приёмник меняла
   композиция без правок модулей.
2. Как оператор smoke, я хочу backend с console-аппендером и местом под кастомный, чтобы видеть
   диагностику инструментов и при желании маршрутизировать её на дашборд.
3. Как разработчик GUI (M1), я хочу подставить свой backend (rolling file), чтобы пользователь
   мог прислать лог с машины.
4. Как разработчик, я хочу имя логгера по классу через делегат, чтобы не тянуть обёртку-либу.
5. Как ревьюер, я хочу запрет диагностических записей в `System.out`/`System.err` из модулей,
   чтобы трюк с перехватом stderr не возвращался.

## Implementation Decisions

- `slf4j-api` implementation в `:infra`; `logback-classic` в `:tools:smoke`; версии —
  `gradle/libs.versions.toml`.
- Property-делегат `by slf4j()` в `:infra` (по классу инстанса; перегрузки по имени/KClass);
  переезд в общий пакет — с первым логирующим потребителем вне `:infra`.
- `FfmpegMediaTool`: logger по классу; уровни warn/info/warn; префикс и `System.err` уходят.
- Smoke: программный конфиг logback (`ConsoleAppender`, pattern с уровнем и именем);
  `System.setErr` + `LineSinkStream` + `composition.stderr` удаляются.
- `:core` не логирует; `:adapters` — через тот же фасад, когда появятся сообщения.
- Пользовательский вывод CLI (usage smoke) — не лог; запрет касается диагностических сообщений.

## Testing Decisions

- Делегат: unit-тест имён логгера (класс, имя, KClass).
- `FfmpegMediaTool`: прежние тесты поведения не трогаются; сообщения диагностики — не контракт,
  ассертов на лог нет.
- Тестовые classpath: logback с программным уровнем OFF — вывод тестов чист; проверки сообщений —
  через контрактные значения (failure-reason), не через лог.
- Smoke: программный конфиг — тонкий тест (аппендер пишет в переданный sink), если появляется
  кастомный аппендер.

## Out of Scope

- Выбор backend GUI (rolling file в `~/.tubeloader/logs`) — фича GUI.
- Структурированные логи/энкодеры — до появления получателя (см. ADR-0013, log4j2).
- Логирование ядра — не появляется: диагностика ядра едет значениями.
