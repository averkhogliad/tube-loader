# Причина отказа в исходах значением

## Problem Statement

Value-исходы контракта (`DownloadResult.Failed`, `LoadMetaResult.Failed`, `MediaResult.Failed`)
несут только класс из набора `DownloadError`. Причина — лучший диагностик, который есть у адаптера
(stderr инструмента, транспортный сбой, статус ответа) — выбрасывается на шве. `DownloadStatus.Failed`
причину имеет, но фасад на value-пути передаёт `null`: заполняет только exception-путь.

`docs/standards/errors.md`: «если шов отдаёт исход значением, значит и причина едет со значением»
и «точный вердикт даёт причина, а не класс» — правило записано, формой контракта нарушено.
Композиция вынуждена reach past interface: smoke держит `LoggingHttpTool`-шпион над портом
`HttpTool`, чтобы увидеть выброшенное адаптером; первый GUI ждал бы ту же дыру.

## Solution

`Failed`-исходы несут причину: `DownloadResult.Failed(error, cause: Throwable?)`,
`LoadMetaResult.Failed(error, cause: Throwable?)`, `MediaResult.Failed(error, cause: Throwable?)` —
обязательный параметр без дефолта: каждый продюсер обязан высказаться явно; `null` — только когда
причины нет. Адаптеры передают реальные исключения: yt-dlp — сбой вызова инструмента с его
собственным текстом, rutube — транспортные отказы со статусом и сообщением. Фасад транслирует:
value-путь — `DownloadStatus.Failed(error, outcome.cause)`, симметрично exception-пути;
`MediaResult.Failed` наследует причину `LoadMetaResult`. Бизнес-исходы (`NotFound`, `Unsupported`)
без причины — не меняются. `LoggingHttpTool` и его тест удаляются: наблюдаемость причин — часть
контракта, а не шпион композиции.

## User Stories

1. Как пользователь, я хочу видеть причину отказа загрузки — текст инструмента или источника,
   чтобы понять, что чинить, не открывая лог.
2. Как фронтенд, я хочу причину в `DownloadState` и `MediaResult`, чтобы не строить собственный
   шпион к портам ядра.
3. Как разработчик композиции, я хочу собрать граф без `LoggingHttpTool`, чтобы диагностика не
   жила копией в каждом композиционном корне.
4. Как агент, я хочу обязательный параметр причины в каждом `Failed`, чтобы дыра не могла
   тихо вернуться новым продюсером.

## Implementation Decisions

- Три `Failed`-исхода получают `val cause: Throwable?` — обязательный параметр, без дефолта.
  `DownloadStatus.Failed` форму не меняет (свой дефолт безвреден, фасад передаёт явно).
- Продюсеры — адаптеры: классификация (`downloadErrorOf` у yt-dlp, маппинг rutube) не меняется —
  класс по знакам, причина — исходный throwable; сбой дистрибуции едет причиной `Failed`.
- Фасад: value-путь несёт `outcome.cause`; exception-путь без изменений; `MediaResult` наследует
  причину из `LoadMetaResult`.
- `LoggingHttpTool` + его тест удаляются; `System.err`-механика smoke — вне скоупа, её закрывает
  фича логирования.
- Изменение обратно несовместимо внутри репозитория: все конструкции `Failed` обновляются одним
  тикетом.

## Testing Decisions

- Contract-набор `SourceAdapterContract`: golden-кейсы отказа ожидают `Failed(error, cause)` —
  причина наблюдаема в сообщении, не только класс (правило `errors.md`: исход и класс различимы
  в наблюдаемом состоянии).
- Таксономии обоих адаптеров: ассерт причины — фрагмент stderr инструмента / статус ответа.
- Фасад: value-путь несёт причину в `DownloadStatus.Failed`; exception-путь — прежние ассерты.
- `ProgressFormatterTest` smoke: причина печатается в строке провала.
- `LoggingHttpToolTest` удалён вместе со шпионом.

## Out of Scope

- Логирование и судьба `System.err`-механики smoke — фича логирования (свой ADR).
- Расширение набора `DownloadError`, уточнение классов — отдельная работа по первому случаю.
- Структурированные причины (sealed-тип детали) — текста сообщения достаточно; пересмотр при
  первой реальной нужде.

## Further Notes

- ADR-0011 фиксирует форму `MediaResult` — Status дополняется ссылкой на этот тикет (по прецеденту
  ADR-0009/0011).
- Принцип уже записан в `errors.md`; меняются формы исходов в таблице бизнес-ошибок.
